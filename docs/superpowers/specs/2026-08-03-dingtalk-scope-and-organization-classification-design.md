# DingTalk scope and organization classification

## Goal

Make conversational DingTalk synchronization appear only after an explicit DingTalk request, offer the operator exactly three scopes (`部门`, `人员`, and `全部`), and classify DingTalk people as teachers or students from their administrative-unit hierarchy through a controlled LLM decision whose result is persisted and inherited by descendants.

## Root causes

The conversation persists `api_provider_id` after an API draft. Hydration currently reconstructs a DingTalk card from that field even when the current source is not API and the latest decision is ordinary conversation. The frontend then renders every non-active card it receives.

The DingTalk adapter already reads departments and people, but the configuration form and task-scoped validation treat `person_entity_kind` as both the requested synchronization scope and a global classification for every person. The resulting synthetic capability names, such as `entity.teacher.read`, can also be presented as though DingTalk exposed a dedicated teacher endpoint. DingTalk's organization API instead exposes departments and people; teacher/student is a domain classification owned by this application.

## User-facing behavior

The secure DingTalk card exposes one field named `同步范围` with exactly these choices:

- `部门`: synchronize administrative units only.
- `人员`: synchronize people and classify each person as teacher or student.
- `全部`: synchronize administrative units and classified people.

The card keeps the generated connection name, root department ID, optional projected-field names, AppKey, and AppSecret. Student-only fields are removed because the operator no longer chooses one global person kind.

Connection and conversation messages use provider-accurate language. A DingTalk permission failure says that department or personnel-directory permission/visibility is insufficient. It never claims that DingTalk denied a dedicated teacher or student API.

## Conversation card lifecycle

The backend is the source of truth for card relevance.

- A card is returned before a source connection exists only when the current decision is `api_configuration` for DingTalk.
- A card may be restored when the current private source is the same conversation-bound DingTalk API connection and the connection still needs attention.
- A stale `api_provider_id` without an API source or current `api_configuration` decision does not produce a card.
- Selecting a non-API source clears stale API-provider context.
- The frontend continues hiding `active` cards and clears its local card whenever a response omits `api_connection`.

This preserves an interrupted DingTalk configuration while preventing unrelated conversation from revealing it.

## Configuration contract

New conversation-bound DingTalk configurations store:

- `sync_scope`: `department`, `people`, or `all`;
- `root_department_id` and projection field names;
- `person_classification_mode`: `organization_unit_llm` for `people` and `all`;
- a server-derived `department_entity_kinds` mapping after successful classification.

The mapping values are only `teacher` or `student`. It is generated by the server and cannot be supplied by the browser. Existing persistent or historical connections that use `person_entity_kind` remain readable for audit and already-bound task replay; new conversation-bound configurations do not use that legacy field.

Scope maps to task entity types as follows:

- `department` -> `department`;
- `people` -> `teacher`, `student`;
- `all` -> `department`, `teacher`, `student`.

The server derives this mapping and ignores client/model attempts to substitute a different set.

## Controlled organization-unit classification

Classification occurs during connection testing, before the connection becomes eligible for task confirmation.

1. The DingTalk adapter authenticates and reads the bounded department tree under `root_department_id`.
2. The classifier receives only stable department IDs, department names, parent IDs, and normalized root-to-node paths. It receives no credentials, tokens, people, phone numbers, email addresses, or provider response bodies.
3. A dedicated versioned Skill asks the LLM to classify administrative branches as `teacher`, `student`, or `unknown` using a strict JSON schema.
4. The backend validates exact department membership, unique IDs, allowed labels, and hierarchy consistency.
5. A classified ancestor is authoritative for its complete descendant subtree. A child cannot override an inherited teacher/student class. Conflicting model output is rejected and retried through the existing bounded model-repair policy.
6. The validated mapping is persisted in the task-scoped connection's private public configuration and frozen into the task binding. Later capture uses this mapping deterministically and does not call the LLM again.

The model classifies organization branches, not individual people. Each person's department memberships are resolved against the persisted mapping. A person inherits the class of the classified ancestor branch.

## Ambiguity and failure handling

For `people` or `all`, configuration remains ineligible when:

- a personnel-bearing branch is `unknown`;
- a person belongs to both teacher and student branches;
- model output omits, duplicates, invents, or contradicts a department;
- the department tree changes between classification and connection testing;
- required department or personnel-directory permissions are missing;
- no classified people are visible.

Failures use safe codes and actionable Chinese text. Unknown branches identify safe department names/paths but never expose credentials or raw person records. The operator can correct DingTalk organization membership and retry with the same form. No unknown person is dropped or guessed silently.

For `department`, the connection test does not call the classifier and does not require personnel-list access beyond what the provider contract strictly needs to validate the selected scope.

## Components and boundaries

- `ConversationCreatePage` renders only backend-relevant non-active cards and clears omitted card state.
- `ConversationApiConnectionCard` owns the three-value scope form and submits no classification mapping.
- The connector API validates `sync_scope`, derives task entity types, and owns connection-context updates.
- A focused DingTalk organization discovery boundary returns a safe department tree independently of person capture.
- A model-backed organization-unit classifier owns prompt/schema validation and returns only a validated branch classification.
- The DingTalk adapter consumes the persisted mapping to project people as `teacher` or `student` while preserving department capture.
- The API materializer and Agent Graph continue consuming the existing canonical `department`, `teacher`, and `student` entity kinds; they do not receive a new generic `person` kind.

## Data and security

AppKey and AppSecret remain confined to encrypted connector secret storage. The LLM request contains organization-unit metadata only. The classifier input hash, Skill version, model-attempt evidence, validated output hash, and connection version are auditable. Conversation responses expose only safe display names, scope, counts, capabilities, and sanitized failures.

## Testing

Automated coverage includes:

- ordinary conversation and non-API source hydration do not reveal a stale DingTalk card;
- explicit DingTalk configuration and interrupted relevant configuration still reveal the card;
- the form offers exactly department, people, and all and submits the chosen scope;
- the browser cannot submit `department_entity_kinds`;
- department scope skips LLM classification and can confirm from visible departments;
- people/all classification receives only department hierarchy metadata;
- teacher/student ancestor results propagate to every descendant;
- conflicting memberships, unknown populated branches, invented IDs, and hierarchy contradictions fail safely;
- the validated mapping is persisted and reused without a second model call during task capture;
- task entity types are derived correctly for all three scopes;
- generic DingTalk permission failures never mention a teacher/student endpoint;
- existing legacy `person_entity_kind` connections remain replayable;
- focused frontend, connector contract, API integration, conversation, materialization, lint, type-check, and production-build gates pass.

## Out of scope

This change does not add a manual per-person classification editor, infer identities from names or personal fields, change DingTalk endpoints dynamically, reuse credentials across conversations, or add the same scope UI to WeCom.
