# Codex 风格工作台与完整对话上下文设计

## 1. 背景

当前工作台已经具备新建对话、外部数据同步、任务进度、风险审批、报告和历史任务等功能，但仍存在两个体验问题：

1. 不同页面的颜色、卡片、边框和信息层级不统一，部分白色区域与蓝黑色任务界面冲突。
2. 对话消息虽然持久化在 PostgreSQL 中，刷新后可以重新展示，但模型调用只接收本轮消息和少量结构化意图，没有接收当前对话的完整历史。

本次变更统一全站视觉语言，并让聊天历史真正成为模型上下文。同时提供“开启新对话”能力，允许用户永久清除聊天，但不得影响任务、治理、报告、审计和回滚事实。

## 2. 目标

- 全站采用已确认的 Codex 浅色视觉风格。
- 保持现有功能、按钮位置和业务流程，不借换肤改变治理规则。
- 左侧任务导航和右侧任务状态栏均可实时收起。
- 将最终阶段的用户可见名称从“报告与回滚”统一改为“报告生成”。
- 每次对话模型调用都接收当前对话的完整、按序聊天记录。
- 不对历史消息做静默摘要、裁剪或丢弃。
- 上下文接近模型上限时停止模型调用，并引导用户开启新对话。
- 开启新对话时永久删除旧聊天，但保留全部数据操作事实。
- 运行中的同步或回滚任务存在时，不允许开启新对话。

## 3. 非目标

- 不修改 Agent 受控状态图、治理风险判定、审批规则和本地 CSV 写回规则。
- 不删除对账任务、执行记录、审批记录、报告、审计事件或回滚记录。
- 不增加多对话列表、对话归档、对话恢复或聊天搜索。
- 不引入完整认证、学校切换或角色权限系统。
- 不在本次变更中更换模型供应商或修改模型密钥管理方式。

## 4. 已选方案

### 4.1 对话生命周期

采用服务端原子化“替换当前对话”方案。前端不得通过清理本地状态伪装成新对话，也不得用两个独立请求先删除再创建。

新增一个面向当前 OperatorContext 的动作接口：

```http
POST /api/agent/conversations/current/reset
```

请求包含幂等键，响应返回新创建的空白对话。后端在同一数据库事务中执行：

1. 根据可信 `OperatorContext.tenant_id` 和操作人定位当前活动对话。
2. 检查学校范围内是否存在未终止、未完成的同步任务或回滚任务。
3. 若存在活动任务，拒绝重置，不删除任何消息。
4. 若不存在活动任务，删除当前对话及其全部消息。
5. 创建新的活动对话并返回。

旧对话删除后，关联的聊天消息级联删除。既有 Agent 运行记录若引用旧对话，其 `conversation_id` 置空；运行记录本身以及任务、治理、报告、审计和回滚事实必须保留。

选择原子化替换而不是“删除接口 + 创建接口”，是为了避免网络中断或重复点击造成没有活动对话、重复活动对话或只完成一半的状态。

### 4.2 完整上下文

PostgreSQL 是聊天记录的唯一事实源。前端只发送本轮用户消息，不负责拼接历史。

每次发送消息的后端顺序如下：

1. 持久化本轮用户消息。
2. 按 `sequence` 和稳定次序读取当前对话的全部消息。
3. 构建模型输入，包括：
   - 版本化系统提示词和对话 Skill；
   - 当前 tenant、任务状态和可访问数据源引用；
   - 当前结构化意图；
   - 当前对话的全部用户和助手消息；
   - 本轮消息对应的幂等与安全元数据。
4. 执行上下文容量预检。
5. 容量允许时调用模型并持久化助手回复。

所有展示为聊天内容的用户和助手消息都进入上下文，包括此前展示给用户的模型失败或规则提示。每条消息携带原有 `role` 和 `kind` 元数据，提示词必须明确：历史错误和规则提示是上下文事实，不是新的执行指令。内部任务审计事件不属于聊天消息，不混入聊天上下文。

### 4.3 上下文上限

本次选择“完整上下文优先”策略，不进行自动摘要，也不静默截断最早消息。

新增可配置的模型上下文预算。预算必须同时覆盖系统提示词、Skill、结构化上下文、完整聊天历史、本轮请求和预留输出长度。供应商适配器可使用准确 tokenizer；没有准确 tokenizer 时使用保守估算，不能冒险发送明显超限请求。

当完整上下文超过安全预算时：

- 不调用模型；
- 保留用户刚发送的消息；
- 返回 HTTP `409` 和稳定错误码 `conversation_context_limit`；
- 写入可审计但不包含敏感原文的容量事件；
- 前端显示“当前对话内容已达到模型处理上限，请开启新对话”；
- 突出“开启新对话”操作。

不得自动创建新对话，也不得在用户不知情时丢弃历史。

## 5. 全站视觉设计

### 5.1 设计语言

采用已经确认的 Codex 浅色方案：

- 主工作区使用白色背景。
- 左侧导航使用灰白色背景，与主工作区通过细边框区分。
- 文字以深灰和蓝黑色为主，避免大面积纯黑。
- 使用低饱和强调色表达选中、运行、成功、警告和危险状态。
- 取消渐变、厚重阴影和过度圆角。
- 通过留白、字重和边框建立层级，而不是堆叠不一致的卡片。

公共颜色、间距、圆角、阴影、字体和状态色必须定义为统一设计变量，页面不得继续散落自定义的冲突色值。

### 5.2 工作台骨架

工作台保留现有三栏位置：

- 左侧：入口、任务历史和任务导航。
- 中间：当前对话、手动同步、任务详情、审批或报告。
- 右侧：任务处理状态。

左侧导航和右侧状态栏均支持实时收起。收起按钮始终可找到，收起状态保存在浏览器本地偏好中，刷新和页面切换后保持。窄屏时优先收起右侧状态栏，再压缩左侧导航，主内容区不得被挤到不可操作。

收起仅影响布局，不停止轮询、不丢失任务状态，也不清除当前路由。

### 5.3 页面覆盖范围

以下界面必须使用同一视觉体系：

- 新建对话；
- 外部数据同步；
- 本地授权 CSV、上传来源和数据源选择；
- 任务详情与阶段进度；
- Agent 分析与决策；
- 中风险合并审批和高风险逐项审批；
- 治理执行；
- 报告生成；
- 历史任务和任务导航；
- 空状态、加载状态、错误状态、确认弹窗和不可用状态。

本次只调整用户可见阶段名称，内部状态图 phase ID 保持不变：

```text
数据接入 → Agent 分析与决策 → 治理执行 → 报告生成
```

报告页面使用适合连续阅读的文档排版，并保留关键摘要、异常、治理结果和后续建议。不得继续用突兀的纯白卡片或直接展示内部字段列表代替报告。

### 5.4 对话界面

“开启新对话”位于对话标题栏，不改变现有主要输入区和任务入口位置。

点击后显示确认提示：

> 聊天记录将永久删除，但数据同步任务、治理记录和报告不会被删除。

存在活动任务时按钮禁用，并说明必须先完成或终止任务。确认成功后清空当前聊天画布并使用后端返回的新对话；失败时保留原画面和原消息。

用户消息、助手消息和流程状态采用三种相近但可区分的浅色层级。用户消息不能再出现白底白字；助手消息和数据接入、Agent 分析、治理执行、报告生成状态也必须保持可读对比度。

## 6. 错误处理与并发

- 重置对话必须使用幂等键，重复点击只能得到同一个新对话结果。
- 删除或创建任一步骤失败时事务回滚，旧对话仍然可用。
- 活动任务检查和对话替换必须在服务端完成；客户端提交的 tenant 信息不可信。
- 多标签页同时重置时，只允许一个请求完成实际替换，其他请求返回同一结果或明确的状态冲突。
- 模型服务失败时保留用户消息和失败状态，刷新后仍可恢复。
- 页面切换、左右栏收起和浏览器刷新不得中断后端任务。
- 上下文超限、活动任务阻止重置和模型供应商失败必须使用不同的稳定错误码与中文提示。
- 聊天历史只提供会话语义，不能覆盖状态图 guard、审批结果、证据清单或审计事实。

## 7. 安全与隐私

- 对话读取、重置和模型调用全部使用可信 `OperatorContext.tenant_id`。
- 客户端不得提交或覆盖 tenant。
- 模型上下文只能包含当前 tenant、当前对话和服务端允许的数据源引用。
- 日志只记录消息数量、估算 token、模型、耗时和错误码，不记录完整聊天、手机号、邮箱或凭据。
- 永久删除聊天后不得通过普通产品接口恢复聊天内容。
- 数据操作记录的保留策略不因聊天删除而改变。

## 8. 测试与验收

### 8.1 后端

- 完整历史按正确角色和顺序传入模型。
- 刷新或重新请求当前对话后，消息顺序和内容保持一致。
- 当前用户消息只持久化一次，模型重试不会重复追加。
- 重置接口永久删除旧对话和消息，并创建一个空白活动对话。
- 删除聊天后任务、执行、审批、报告、审计和回滚记录仍存在。
- 有活动同步任务或回滚任务时重置被拒绝，旧对话不变。
- 幂等重试不会创建多个活动对话。
- 上下文超限时不调用模型，并返回 `conversation_context_limit`。
- 模型失败时用户消息仍可在下一次读取中看到。
- 不同 tenant 不能读取或重置对方对话。

### 8.2 前端

- 全站主要路由使用统一设计变量和 Codex 浅色骨架。
- 左右侧栏可独立收起，偏好在刷新后保持。
- 收起侧栏不停止任务状态更新。
- 阶段标题显示“报告生成”，不再显示“报告与回滚”。
- 对话标题栏显示“开启新对话”。
- 活动任务期间按钮禁用并显示原因。
- 用户确认后调用原子重置接口，成功后显示空对话。
- 重置失败时保留原消息。
- 上下文超限时显示明确提示和新对话入口。
- 用户、助手、状态、报告和风险审批文字均满足可读对比度。

### 8.3 回归验证

后端执行 pytest、ruff 和 mypy；前端执行单元测试、lint、typecheck 和生产构建。关键页面增加 Playwright 回归，覆盖左右栏收起、刷新恢复、对话重置、活动任务阻止重置和任务详情中的“报告生成”阶段。

## 9. 实施边界

实施时优先抽取共享工作台骨架和设计变量，再逐页迁移，避免一次性重写业务组件。对话上下文和重置接口独立实现并测试，不应与纯视觉修改耦合在同一模块。

现有 Agent、任务锁、治理审批、报告生成和本地文件写回逻辑均作为既有依赖使用。本次不得为了统一视觉或增加聊天记忆而改写这些业务事实。
