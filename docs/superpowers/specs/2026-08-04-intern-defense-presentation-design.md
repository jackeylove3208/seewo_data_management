# 实习课题答辩演示设计

## 沟通目标

在 15 分钟内，让实习课题答辩评委理解：本项目并非简单调用大模型做数据比对，而是围绕学校组织数据治理，把确定性后端、受控 Agent Graph、证据受限 Skill、人工审批、验证与回滚组合成一条可执行、可恢复、可审计的闭环；系统当前形态来自真实问题驱动下的持续演进。

## 叙事策略

采用“问题驱动的技术演进型”叙事。前半段回答为什么采用当前设计以及各组件如何协作，中段沿数据与治理流程解释系统怎样运行，后半段用 Git 提交和问题修复记录证明设计不是空洞理论。

全篇约 15 页，每页只承担一个核心论点。正文不展示制作过程或演讲提示；必要讲解写入演讲者备注。

## 视觉策略

- 画面比例为 16:9，整体采用深蓝、青色和暖橙点缀的技术答辩风格。
- 标题使用结论句，而不是“项目背景”“系统架构”等目录式标题。
- 核心架构图、Agent 状态流和数据闭环使用少量原生形状与连接线表达。
- Git 演进部分使用时间线和“旧设计—暴露问题—当前设计”的对照关系。
- 避免密集卡片、长段文字和装饰性图片，优先展示系统关系、约束和因果。
- 每页底部保留简洁页码；代码提交、仓库文档和源文件作为演讲者备注中的来源。

## 页序设计

### 1. 封面

标题为“基于 AI 的组织架构三方数据分析与治理系统”，副标题强调“从数据差异发现到安全治理闭环”。保持极简。

### 2. 多系统独立维护，数据偏差不是偶发异常

用希沃魔方、钉钉/企业微信、教务系统三类来源围绕教师、学生、班级、部门的关系说明问题。落点是缺失、冗余、属性冲突和结构差异会持续产生。

### 3. 项目目标不是比对一次，而是持续治理一次

展示“接入—识别—解释—决策—执行—验证—回滚”的闭环。强调系统交付物是可运行治理链路，不是实验脚本或一次性报告。

### 4. 纯规则、单 Agent、自由多 Agent 都无法同时满足准确性与安全性

比较四种方案：纯规则缺少语义适应性；单 Agent 上下文过大且权限过宽；自由多 Agent 难以恢复和审计；当前方案由确定性后端拥有状态与权限，Agent 只在受控范围内推理。明确说明选择的代价是合同和状态管理更复杂，但换来可控性。

### 5. 当前框架把推理能力包在确定性工程边界内

展示六个组成：对话与工作台、任务与持久化状态机、Agent Supervisor、专业 Skill/Sub-agent、工具授权网关与连接器、事实与审计存储。标明第三方权威来源只读，希沃目标是唯一治理写入端。

### 6. Agent Graph 用服务端节点固定业务边界

讲清节点：`materialize_sources`、`ingest_and_normalize`、`analyze_batches`、`clarify_identity_conflicts`、`plan_governance`、人工审批 Gate、`execute_and_verify`、`generate_report`，以及独立回滚任务。解释节点拥有的输入、输出和允许动作不同。

### 7. Supervisor 每轮只选择一个允许动作，不能自行改写流程

用一次流转循环说明：服务端读取持久化状态并计算 `allowed_actions`；Supervisor 选择一个动作；Skill 在阶段工具边界内执行；结果校验并持久化；服务端重新计算下一步。突出学校锁、租约、检查点和人工 Gate。

### 8. Skill 从提示词升级为可验证的执行合同

拆解一个 Skill 的组成：名称与版本、阶段、输入 Schema、输出 Schema、允许工具、可信证据边界。以 `reconcile-entity-batch`、`execute-approved-governance-plan` 和 `generate-agent-governance-report` 说明分析、执行、报告权限互不混用。

### 9. 数据先变成冻结证据，再进入 AI 分析

展示数据路径：CSV/API/数据库或远程文件输入；下载或读取后形成不可变快照；字段映射和六字段标准化；敏感信息令牌化；构建身份索引和工作项；按批次交给 Skill。强调 AI 不直接接触凭据，也不从任意来源扩展证据。

### 10. 分析结果不能直接写库，必须经过治理编译与验证

展示治理路径：finding 与方案解释；后端风险政策；冲突澄清；人工批准；服务端把批准事实编译为固定操作；幂等执行；读取实际结果验证；生成事实绑定报告。说明风险与执行参数由后端拥有，而不是由模型决定。

### 11. 回滚不是“撤销按钮”，而是新的受控治理任务

用 `before / after / current` 三方比较解释为什么旧快照不能直接覆盖当前数据。只允许从已验证 mutation 生成补偿操作；冲突时停止并交给人工。独立 task、run、学校锁、审批、报告保证回滚本身也可审计。

### 12. 架构经历了三代工作流，而不是一次设计完成

时间线展示 `legacy-v1 → new-agent-v1 → agent-graph-v1`：早期完成差异分析与确定性治理；随后增加持久化 Agent 运行时；最终引入受控图、阶段 Skill 和证据工具。解释为什么保留不可变 `workflow_version` 和隔离 Worker，而不是原地改写旧任务。

### 13. Skill 演进的方向是更窄、更专业、更可恢复

对照早期 legacy Skill 与当前 Skill：从单条差异解释、治理计划说明，演进到接入检查、规范化、实体对账、冲突解释、执行验证、失败分析、报告与回滚；再增加分析模板 Skill。结论是 Skill 数量增加不是堆 Prompt，而是在收窄责任与权限。

### 14. 真实故障推动了批次、检查点与模板机制

选取四组 Git 证据：钉钉人员分类从不确定结果改为规则优先、模型二选一；大批次长 JSON 改为最多 10 项；模型失败后增加工具检查点与安全重放；同构人员使用模板、复杂多候选人员隔离分析。每组使用“现象—错误假设或旧方案—根因—修正”结构。

### 15. 最终形成的是一套可控 AI 工程方法

收束为五条原则：确定性系统拥有事实与权限；AI 处理歧义而非替代规则；每次推理有证据和合同边界；治理必须审批、验证和可回滚；系统通过失败记录持续演进。最后说明当前边界：CSV 已端到端，API/数据库连接器仍按能力失败关闭，后续重点是扩展连接器和建立量化效果评估。
