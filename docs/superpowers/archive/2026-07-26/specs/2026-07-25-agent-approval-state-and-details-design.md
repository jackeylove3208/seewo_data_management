# Agent 审批状态与操作明细修复设计

## 目标

修复 `agent-graph-v1` 在风险汇总和人工审批之间的状态不一致，并让操作员在审批前看清具体对象、修改内容和风险原因。本次不改变三段式对账分析算法，也不扩大高风险范围。

## 现状与根因

`analyze_actionable_batches` 和 `aggregate_risk` 两个节点目前复用了同一个 `aggregate_risk` action。生产执行器仅按 action 类型分派，因此从分析节点进入风险汇总时就提前执行了风险汇总、持久化审批门并请求人工暂停。

状态图提交阶段拒绝在非人工门节点暂停，但执行器已经通过独立事务提交了审批门。任务重试后又写入相同的确定性调用记录，触发唯一约束，最终产生以下不一致：

- 图状态仍停留在 `analyze_actionable_batches`；
- 业务阶段仍显示“Agent 分析与决策”；
- 数据库中已经出现待审批门；
- 前端错误地显示可点击按钮；
- 审批接口按当前图游标校验并返回 `Gate cursor is stale`。

## 状态图修复

将风险汇总入口与风险汇总执行拆成两个有明确语义的 action：

- `enter_aggregate_risk`：只从分析节点或冲突处理节点转换到 `aggregate_risk`，不得写审批事实，不得暂停。
- `aggregate_risk`：只允许在 `aggregate_risk` 节点执行，汇总高风险 finding、冻结审批成员并转换到 `wait_high_risk_approvals`。存在待审批组时在该人工门节点暂停。

生产执行器必须同时校验当前节点和 action 类型，禁止同一副作用 action 在错误节点执行。确定性调用记录必须支持同一图游标和 action 的幂等重放，避免进程中断后的安全重试演变成持久化冲突。

历史上已经失败且游标错位的任务不自动续跑。界面应将其审批标记为不可操作，操作员终止或删除后重新创建任务。

## 审批可操作性

进度接口为每个审批门返回 `actionable` 和不可操作原因。只有同时满足以下条件才可审批：

- 门状态为 `pending`；
- 任务和图状态为 `waiting_human`；
- 当前节点与门类型一致；
- 门游标是当前图游标对应的冻结游标。

前端只在 `actionable=true` 时显示同意和拒绝按钮。过期、失败或错位的审批门保留审计可见性，但显示“审批不可用”以及中文原因。

当有效高风险审批已经生成时，图节点必须位于 `wait_high_risk_approvals`，进度接口的 `business_stage` 必须为 `governance_execution`，顶部阶段图标随服务端事实进入“治理执行”。

## 高风险范围

服务端风险策略只将以下操作判定为高风险：

- 删除任何实体记录；
- 更新已有学生记录的手机号字段。

新增学生即使包含手机号，也不进入高风险审批。模型输出的风险等级不能覆盖服务端规则。

## 审批明细

每个审批组继续按问题类型、实体类型、操作和字段集合合并，但接口增加逐条只读明细。明细从冻结的 finding 成员关联到工作项、规范化输入和推荐治理方案，不接受客户端补充或覆盖。

每条明细至少包含：

- finding ID；
- 实体类型；
- 显示名称；
- 编号；
- 学生班级或其他可用定位信息；
- 来源行号或稳定定位符；
- 中文操作说明；
- 中文问题类型和分析原因；
- 修改前和修改后的字段列表。

删除操作必须明确显示删除哪个目标记录以及删除原因。修改操作必须按字段展示修改前后值。新增操作必须显示将创建的权威记录内容。

学生手机号在接口和界面中只显示脱敏值，不能返回原始手机号。邮箱和其他联系方式也采用脱敏展示。姓名、编号、班级用于操作员确认具体对象。

审批组可一次决定同类多条记录，界面在卡片中提供可展开的明细列表。成员很多时按固定顺序分页或分段展示，但审批决定仍绑定冻结成员集合，不能因前端筛选改变审批范围。

## 数据接入事件呈现

不改变数据接入的 Agent 调用和批次算法。前端为 `graph.transitioned` 增加中文动作映射，至少覆盖：

- 第三方数据结构检查；
- 希沃数据结构检查；
- 第三方和希沃数据规范化批次；
- 输入合同验证；
- 身份索引、工作项构建、AI 分析、风险汇总和审批等待。

未知内部事件仍可使用通用审计文案，但正常状态转换不得再全部显示为“系统已记录一条内部审计事件”。

## 错误处理

- 错误节点执行副作用 action 时，服务端应在写入审批事实前拒绝。
- 同一确定性调用的安全重试应返回既有结果或保持幂等，不得触发唯一约束错误。
- 前端收到 `stale_graph_gate` 时刷新图进度，并将该门标记为不可操作，不重复提交。
- 审批成功后立即显示“已允许”或“已拒绝”，随后刷新服务端状态确认。

## 验收测试

后端测试必须证明：

1. 分析节点进入风险汇总时不创建审批门、不暂停。
2. 风险汇总节点只创建一次冻结审批门，并进入 `wait_high_risk_approvals`。
3. 相同 action 重试不会生成重复确定性调用或重复审批成员。
4. 只有当前人工门可审批，过期门在进度接口中不可操作。
5. 有待审批门时业务阶段为“治理执行”。
6. 新增学生不是高风险，删除和学生手机号更新仍为高风险。
7. 审批接口返回具体删除对象和字段修改前后值，学生手机号经过脱敏。

前端测试必须证明：

1. 可操作审批显示按钮，过期审批显示不可用原因。
2. 审批成功后卡片立即显示“已允许”或“已拒绝”。
3. 删除和修改审批能够展开查看逐条中文明细。
4. 状态图进入审批等待后顶部进入“治理执行”。
5. 常规图转换展示明确中文进度，不再落入通用内部审计文案。

最后运行后端测试、静态检查、类型检查，以及前端单元测试、lint、类型检查和构建。涉及状态图完整生命周期的测试必须覆盖 PostgreSQL 持久化约束。
