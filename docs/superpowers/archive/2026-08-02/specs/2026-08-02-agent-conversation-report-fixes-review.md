# Agent 对话与异常报告问题复盘及修改方案

日期：2026-08-02

## 结论

本次四个现象不是同一个故障，但其中前三个共享一处核心设计问题：前端没有区分“用户消息是否已被服务端接收”和“模型是否成功生成回复”。后端实际上会先保存用户消息，再调用模型；模型失败后前端却把原问题改写成“消息未被接受”，造成界面、持久化记录和真实处理状态互相矛盾。

第四个现象的根因是报告数据结构与页面展示都只面向“正常完成的治理任务”。任务在异常阶段终止时，服务端仅生成固定标题和摘要，没有保存终止阶段、原因、已完成工作和未完成工作；此时问题及变更事实也可能尚未产生，前端便显示两个空列表，看起来像“报告没有内容”。

## 问题一：消息显示未被接受，同时模型回复失败

### 现状与数据流

1. `frontend/src/features/task-create/ConversationCreatePage.tsx` 提交消息后先显示占位文案。
2. `backend/app/api/routes/agent.py` 在调用模型前已经通过 `append_conversation_message` 持久化用户消息，并提交事务。
3. 模型输出不符合合同或模型服务报错时，后端再持久化一条 `kind="error"` 的助手消息，并返回 `502 conversation_model_error`。
4. 前端统一进入 `catch`，把本地用户消息改写为“消息未被接受。”。

因此，“消息未被接受”在模型失败场景中是错误描述：消息已经被后端接收和保存，只是本轮助手回复生成失败。页面刷新后，后端保存的原问题又会重新出现，进一步造成前后不一致。

### 模型失败的放大因素

`backend/app/ai/conversation_agent.py` 会重试无效输出，但每次重试使用同一份请求，没有把上次的字段校验错误反馈给模型进行结构修复。连续生成相同无效 JSON 时，三次调用都会失败。当前 API 又把 `ConversationModelResponseError` 和 `ModelProviderError` 合并为同一个公开错误码，且该链路没有记录可区分的安全诊断事件，所以仅凭页面无法判断是供应商不可用、超时，还是响应 schema 校验失败。

这里能确认的是“重试缺少修复反馈”和“错误分类不可观测”；某一次线上失败究竟属于哪类，仍需结合模型请求日志确认，不能只依据统一文案推断。

### 修改方案

- 保留用户原问题，不再把模型失败场景改写成“消息未被接受”。
- 将错误分为两类：
  - 请求在进入服务端前失败、或被 `4xx` 输入校验拒绝：显示“发送失败”，允许保留草稿并重发；远程链接等敏感输入继续遵守现有的回显脱敏规则。
  - 用户消息已经持久化、但模型生成失败：原问题正常显示，助手气泡显示“回复生成失败”，提供“重新生成回复”操作，重试时不得再次新增一条相同用户消息。
- 后端为已持久化但回复失败的消息保存可重试关联标识，例如 `reply_status`、`user_message_id` 或单独的回复尝试记录；重新生成必须绑定原消息并保证幂等。
- 对 `ConversationModelResponseError` 使用带校验反馈的 JSON 修复请求；供应商错误继续做有限次数重试，不把两类错误混在同一个内部指标中。
- 后端记录安全诊断字段：`conversation_id`、`user_message_id`、失败类别、尝试次数、provider、model、request_id。禁止记录原始敏感消息和无效模型全文。
- 构造下一轮模型历史时，明确排除仅供 UI 展示的助手错误文案，避免“请稍后重试”进入业务对话上下文。

## 问题二：同步助手直接显示“对话服务暂时不可用”

### 根因

该文案不是模型生成的回复，而是 `ConversationCreatePage.tsx` 初始化时的前端固定兜底。页面会依次读取当前对话、必要时创建对话；这两个请求中的任意一个失败，都会被同一个无参 `catch` 吞掉并追加该助手错误气泡。

当前实现存在三个问题：

- 网络失败、后端 `503`、鉴权失败、功能开关关闭以及其他 API 错误全部显示成同一句话，无法指导用户处理。
- 初始化只尝试一次，没有重试按钮，也没有自动退避重试。
- 服务连接故障被伪装成“同步助手说了一句话”，容易被理解为模型回答。

代码中未发现字面量 `**：**`，当前 JSX 也没有 Markdown 渲染：角色名由 `<strong>` 渲染，正文由 `<p>` 渲染。如果线上确实显示星号，应进一步核对部署版本或截图；这不是当前仓库源码能够直接复现的现象。

### 修改方案

- 初始化失败改用页面级 `Alert`/连接状态条，不写入对话消息列表，也不持久化为对话内容。
- 保留原始 `ApiError.code` 和 HTTP 状态，分别展示“无法连接后端”“登录状态失效”“对话功能未启用”“读取对话失败”等安全文案。
- 增加明确的“重新连接”按钮；仅对网络错误和可恢复的 `5xx` 做带上限的指数退避重试。
- 成功恢复后自动移除连接错误提示，不在聊天记录中留下伪消息。
- 增加初始化链路指标，分别统计 `currentConversation` 与 `createConversation` 的失败率和耗时。

## 问题三：用户问题被替换成“消息已提交，正在安全处理”

### 根因

这是前端在 `sendMessage` 中主动写入的占位文案。只有接口成功返回后，占位文案才会被 `accepted_message` 替换；请求耗时、失败或页面离开期间，用户看不到自己刚刚输入的内容。

引入该占位的原意是避免未经后端脱敏的远程链接直接回显，但它被应用到了所有普通问题，牺牲了对话的即时性和可理解性。

### 修改方案

- 普通文本提交后立即显示用户原问题，并在气泡旁显示独立的 `sending/sent/reply_failed` 状态，不再用状态文案覆盖正文。
- 含 URL 或其他需要服务端脱敏的消息继续采用安全策略：可以先显示“正在校验链接”的专用占位，服务端返回 `accepted_message` 后替换；校验拒绝时不回显密钥、查询参数等敏感内容。
- 不论成功或失败，消息正文和投递状态使用不同字段管理，避免再次出现“状态覆盖内容”。

## 问题四：异常终止分析报告没有正文内容

### 根因

`backend/app/agent_graph/production_executor.py` 对 `termination_report` 明确绕过报告模型，只生成以下叙事字段：标题、固定摘要、事实引用和 `degraded`。这是为了保证终止流程不依赖模型，设计本身合理，但报告内容不足。

`build_agent_report_facts` 当前主要收集：

- `findings`：已经形成的问题；
- `excluded_findings` 和 `input_diagnostics`：已经标记的输入异常；
- `mutations`：已经编译或执行的治理操作。

如果任务在数据接入、模型阻断或首批分析前终止，上述集合可能全部为空。前端 `AgentReportPage.tsx` 又固定渲染“问题分析与治理方案”和“治理执行结果”，空集合分别显示“没有需要治理的问题”和“本任务没有修改目标数据”。这不仅显得没有内容，还可能把“尚未分析”误表述成“没有问题”。

异常输入报告也有类似降级缺口：报告模型失败时，fallback 叙事只有固定摘要，不生成 `input_exception_analyses`；若异常标记事实也尚未完整落库，页面就没有可展示的异常原因。

### 修改方案

- 给报告事实增加服务端生成的 `termination_context`/`failure_context`，至少包含：
  - 终止或失败原因码及安全中文说明；
  - 请求终止时间、实际终止时间；
  - 终止时所在 graph node、业务阶段和最近完成阶段；
  - 已完成工作摘要、待处理工作摘要；
  - 已产生的问题数、审批数、已执行/未执行操作数；
  - 数据是否发生修改，以及修改是否完成服务端验证；
  - 模型阻断时的安全失败类别和尝试次数。
- 终止报告继续采用确定性服务端生成，不强依赖模型；模型只可润色，不能决定事实或阻塞终态。
- 异常输入报告的 fallback 应根据 `input_diagnostics.reason_counts` 确定性生成每个原因的分析、影响和建议，保证模型不可用时仍有正文。
- 前端按终态分支渲染：
  - `terminated`：显示“为什么终止、停在哪一步、已完成什么、未完成什么、是否改过数据”；
  - `abnormal_input`：优先显示异常原因、影响范围和修复建议；
  - `failed`：显示安全错误说明和可执行的下一步；
  - `completed`：继续显示现有问题分析与执行结果。
- 对“尚未执行分析”使用准确空状态，不得显示“没有需要治理的问题”。

## 建议修改范围

| 优先级 | 文件或模块 | 修改重点 |
| --- | --- | --- |
| P0 | `frontend/src/features/task-create/ConversationCreatePage.tsx` | 原问题即时显示；消息正文与投递/回复状态分离；按错误码处理；初始化错误移出聊天记录 |
| P0 | `backend/app/api/routes/agent.py` | 明确消息已接收但回复失败的 API 语义；支持对原消息幂等重新生成；错误分类与观测 |
| P0 | `backend/app/ai/conversation_agent.py` | 无效 JSON 使用校验反馈修复；区分 schema 失败与 provider 失败 |
| P0 | `backend/app/agent_graph/production_executor.py` | 为终止、异常输入和失败报告写入确定性的上下文事实 |
| P0 | `frontend/src/features/reports/AgentReportPage.tsx` | 按终态展示正文；修正“尚未分析”的空状态 |
| P1 | `backend/app/agent_runtime/csv_governance_handlers.py` | 扩展报告事实构建，聚合阶段、终止、失败及待处理工作 |
| P1 | API schema 与数据库模型/迁移 | 增加消息回复状态或回复尝试关联；必要时扩展报告事实合同版本 |

## 测试与验收标准

### 前端测试

- 提交普通问题后，在请求完成前立即看到原问题，看不到“消息已提交，正在安全处理。”。
- `conversation_model_error` 时原问题不变，只新增可重试的助手错误状态。
- 点击重新生成不会再次调用“发送用户消息”语义，也不会产生重复用户气泡。
- `422` 远程链接拒绝时仍不泄露 URL 查询参数或密钥。
- 初始化失败显示连接告警和重试按钮，聊天列表中不出现伪助手消息。
- 终止、异常输入、失败、正常完成四种报告都有各自的正文和准确空状态。

### 后端测试

- 模型失败后，用户消息只持久化一次，回复尝试与该消息关联。
- 重试回复具备幂等性，并且不会污染或重复对话历史。
- 下一轮模型上下文不包含 UI 错误助手消息。
- schema 无效时会收到结构修复反馈；provider 错误和 schema 错误产生不同诊断类别。
- 在数据接入、分析、审批、执行四个阶段分别终止任务，报告均包含对应的阶段、原因、已完成/未完成摘要和数据修改状态。
- 报告模型完全不可用时，终止报告和异常输入报告仍有确定性正文。

## 推荐实施顺序

1. 先统一消息状态语义并补齐失败重现测试，解决错误改写用户问题的问题。
2. 再增加回复幂等重试和模型错误分类，降低“有效回复生成失败”的发生率并获得可诊断证据。
3. 将初始化错误移出聊天记录，补齐连接重试体验。
4. 扩展终止/失败报告事实合同，再按终态重构前端报告展示。
5. 最后执行前后端完整质量门禁，重点回归远程链接脱敏、并发消息 claim、任务终止和报告不可变性。
