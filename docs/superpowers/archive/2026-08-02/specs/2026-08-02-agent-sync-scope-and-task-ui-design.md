# Agent 同步范围与任务 UI 修复设计

## 目标

修复 AI 对话创建同步任务时的三个相关问题：用户明确要求“同步全部”时必须覆盖部门、教师和学生；右侧任务处理状态只在任务已经创建且尚未结束时出现；终止确认因陈旧 gate 返回 `409 Conflict` 时不能把用户困在弹窗中。

## 已确认的产品行为

- “同步全部”不是第四种实体类型，而是 `department`、`teacher`、`student` 三种实体的完整集合。
- 用户明确表达“同步全部”“全量同步”“全部都同步”等无实体限定的全量意图时，服务端必须确定性展开为三种实体，不能只依赖模型是否枚举完整。
- 若句子包含“只”“仅”“不要”“排除”“除了”等限制语义，或“全部学生”这类明确实体限定，则不得强制展开为三种实体，仍由对话模型按原意解释。
- 三种实体全部选中时，开始确认卡显示“全部（部门、教师、学生）”，让用户能直接确认这是完整范围。
- 右侧“任务处理状态”在任务启动请求成功前不渲染；任务进入 `completed`、`terminated` 或 `failed` 后收起。`running`、`terminating`、`waiting_human` 和 `blocked_model_error` 等非终态仍显示，因为任务仍占用执行上下文或需要用户处理。
- 状态栏不渲染时，聊天区域使用完整可用宽度，不保留空白状态栏列。
- 终止确认 gate 返回 `409` 表示页面持有的确认已过期、已决定或不再可操作。前端关闭旧弹窗，刷新任务、图和事件状态，并在弹窗外显示后端错误；用户不会被迫反复点击同一个陈旧确认。
- 非 `409` 的终止失败保留弹窗，允许用户根据错误重试或选择继续执行。
- 对话创建页和 Agent 任务详情页采用相同的陈旧终止确认恢复规则。

## 方案比较

### 采用：服务端确定性归一化，加前端按真实状态渲染

在模型输出解析后、来源与权限校验前，服务端识别无歧义的全量措辞并把实体范围归一化为三个规范实体。模型 Skill 同时明确全量语义，减少模型输出偏差。前端只负责展示服务端确认范围和真实任务状态。

这个方案保证确认卡和最终任务使用同一份服务端意图，也能让 API 连接器权限校验针对完整范围执行。代价是需要同时补充后端语义测试和前端交互测试。

### 未采用：只修改模型提示词

改动较少，但模型仍可能漏掉一个实体，不能为任务范围提供确定性保证，也无法覆盖已有模型供应商的输出波动。

### 未采用：前端看到“全部”后自行补齐

前端补齐会使确认卡、持久化意图和后端实际任务范围可能不一致，破坏服务端作为可信意图来源的边界，因此不采用。

## 架构与数据流

### 全量范围归一化

`ConversationSupervisorAgent.reply` 在解析 `ConversationAgentDecision` 后执行一个纯函数归一化步骤。该步骤只处理 `intent_update` 和 `start_confirmation`，并使用本轮原始 `ConversationAgentContext.message` 判断是否为无歧义全量请求。

归一化规则要求消息同时包含同步类动作和全量词，且不包含实体限定或排除词。满足时把 `entity_types` 替换为按规范顺序排列的 `department`、`teacher`、`student`。随后继续执行默认目标选择和来源/API 权限校验。这样不支持某类实体的 API 连接会得到正常的权限澄清，而不是静默缩小范围。

对话 Skill 明确写出“全部/所有/全量”在无实体限定时代表三种实体，并提升 Skill 版本。路由继续从归一化后的 decision 构建、持久化并返回同一份 intent 和 start confirmation，无需前端猜测用户原话。

### 状态栏生命周期

对话创建页从任务状态派生 `showTaskStatusRail`：存在任务且状态不是 `completed`、`terminated`、`failed` 时为真。只有为真时，工作区添加双列布局类并渲染 `TaskStatusRail`；否则渲染单列聊天区域。

聊天内的任务结果卡不受此条件影响，终态结果和错误仍保留在对话中。独立任务详情页本身就是任务上下文，因此保留其状态栏，不应用创建页的隐藏规则。

### 陈旧终止确认恢复

两个页面提交 termination gate decision 时检查 `ApiError`：

- 成功：关闭弹窗并刷新或更新任务状态。
- `409`：先清除本地 termination gate，确保弹窗立即关闭；再刷新可用的任务、图和事件查询；最后在页面级错误区域展示后端返回的信息。
- 其他错误：记录错误但保留 gate，允许重试。

对话创建页没有统一查询缓存，因此通过现有 `task` 和 `graph` API 主动获取一次最新状态，并让后续轮询继续收敛。任务详情页复用现有 React Query `refetch`。

## 错误处理

- 全量语义存在限制词或实体限定时不做确定性扩展，避免把“同步全部学生”误解为同步三类实体。
- 后端全量归一化不绕过连接器支持范围、可见范围或权限校验。
- `409` 的错误信息显示在模态框外；即使刷新请求失败，旧模态框也保持关闭，常规轮询仍会再次同步状态。
- 非冲突类网络或服务器错误不被误判为陈旧确认，保留原有重试能力。

## 测试策略

后端单元测试覆盖：

- “同步全部”把模型漏报的实体扩展为部门、教师、学生。
- “同步全部学生”和带排除词的请求不会被扩展。
- 扩展发生在 API 连接权限校验前，不支持完整范围时返回澄清。
- Skill 内容和版本声明包含确定性的全量语义。

前端组件测试覆盖：

- 尚未创建任务时不存在“任务处理状态”。
- 发送消息并收到开始确认时仍不显示状态栏。
- 启动任务成功后显示状态栏和双列布局。
- 三种实体的确认文案显示“全部（部门、教师、学生）”。
- 任务进入完成、终止或失败状态后状态栏隐藏且布局恢复单列。
- 对话创建页和任务详情页的 termination decision 返回 `409` 后，弹窗关闭、错误可见并触发状态刷新。
- 非 `409` 失败仍保留终止弹窗。

验证包括相关 Vitest、pytest 单元测试，以及前端 lint、typecheck 和 build。变更完成后再运行受影响套件和仓库规定的静态检查。
