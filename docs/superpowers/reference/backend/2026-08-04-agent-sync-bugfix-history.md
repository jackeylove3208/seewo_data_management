# Agent 同步问题修复历程

本文记录 2026 年 8 月 3 日至 8 月 4 日围绕钉钉人员分类、Agent 模型失败恢复和 CSV 大批量分析所做的排查与修复。文档只保留脱敏后的技术事实，不包含真实人员数据、连接凭据或模型响应原文。

## 最终结果

- 钉钉人员必须被归入“教职工”或“学生”，不再产生无法明确分类的第三种结果。
- 行政单元只有一类明确证据时由服务端直接分类；两类证据同时存在或都不存在时交给模型二选一。
- 钉钉组织快照和人员分类决定可以复用，避免全体或人员范围重复拉取、重复分析。
- 模型工具调查进度按调用持久化，失败重试从检查点继续，不再从头重复已经完成的工具读取。
- 常规分析批次恢复为最多 10 项；大量同构的 `target_extra` 和 `target_missing` 只生成一次通用模板，其余人员由服务端套用。
- CSV 批次中少量复杂人员不会再拖累整批：最大可模板化人群走模板，复杂人员使用独立、收窄证据范围的完整分析调用。
- 最终合并提交为 `2fdbcb8 fix: isolate complex CSV analysis items`，合并后完整后端测试结果为 `1308 passed, 4 skipped`。

## 问题演进

### 1. 钉钉全体和人员范围连接缓慢且无法分类

最初现象是：对话 Agent 连接钉钉后，范围选择“全体”或“人员”时连接明显变慢，并提示部分人员的行政单元无法判断为教职工或学生；选择“部门”则正常。

早期实现让模型根据组织单元判断人员身份，但把模型无法确认的结果继续暴露给业务流程。这同时带来两个问题：模型调用放大了全量人员范围的等待时间；模型输出的不确定状态违背了业务上必须二分类的要求。

修复策略分为四层：

1. 行政单元只出现“学生”证据时直接归为学生，只出现“教职工”证据时直接归为教职工。
2. 两类证据同时出现或都不存在时才调用模型，模型合同只允许返回学生或教职工。
3. 分类结果持久化并绑定冻结的组织快照，后续处理复用已有决定。
4. 同一次连接复用钉钉组织快照，避免范围检查、人员展开和分类阶段重复获取组织树。

### 2. 大改动更容易触发四次模型尝试失败

随后出现两类相近错误：

- 模型输出未通过结构化结果校验。
- 模型服务未能完成处理。

小范围同步通常正常，而大范围 CSV 同步更容易失败。排查确认“本阶段共进行了 4 次模型尝试”表示一个语义 Skill 最多尝试四次，不等同于一次调用固定进行了四个工具步骤，也不直接等同于 HTTP 超时。

第一轮缓解包括：

- 将模型分析批次限制为最多 10 项，并处理旧的大批次重新规划。
- 将模型请求超时延长到 120 秒。
- 减少一次响应需要生成的人员分析数量，降低长 JSON 被截断或结构漂移的概率。

### 3. 模型失败后工具调查从头开始

Agent 的分析过程需要通过工具逐步读取冻结证据。原先只要最后一次模型请求失败，前面已经完成的工具调用对下一次尝试帮助有限，下一次语义尝试可能重新调查相同内容。

修复后，每个已授权工具调用都会保存参数描述、结果哈希、模型轮次和证据绑定。重试时服务端先验证冻结上下文和结果哈希，再重放已经完成的工具结果，模型从最近检查点继续。

恢复逻辑同时保证：

- 不重放未授权工具。
- 不跨任务、运行、图游标或 action 使用检查点。
- 证据清单变化时拒绝恢复，而不是静默使用旧结果。
- 前一次调用已经完成时直接复用完成结果。

### 4. 失败报告只有“用户手动终止”

任务在模型错误后进入安全暂停，操作人最终只能终止任务，旧报告因此只记录最后的终止动作，丢失了真正的前置失败原因。

修复后，失败记录会保留安全错误分类、阶段、尝试次数、HTTP 状态类别、耗时、请求 ID 和结构化修复反馈。终止报告优先解释原始模型或工具失败，再把人工终止说明为后续处置动作。

### 5. CSV 大量缺失或多余人员仍产生长 JSON

为避免每个人都要求模型重复生成相同文字，系统增加了分析模板：对于同构的 `target_extra` 或 `target_missing`，模型只分析一个代表样本并输出通用模板，服务端将模板安全套用到同组人员。

这项修改保留 10 项批次吞吐，同时显著缩短模型输出。批次还需要按差异类型分组，避免旧 CSV 分组方式把不同异常混到一起。

### 6. 最终的“模型响应不是有效 JSON”问题

最后一次失败发生在 CSV 分析阶段，界面显示模型连续四次返回无效 JSON。安全元数据表明：

- 四次 HTTP 请求均返回 `2xx`。
- 每次只有一次传输尝试，不是网络超时重试耗尽。
- 失败 Skill 是 `reconcile-entity-batch`。
- 失败批次包含 10 个学生 `target_missing` 工作项。
- 前面的模板批次已经成功。

最初曾根据字段存在情况怀疑“一个人员缺少班级字段导致模板 profile 不一致”。继续检查身份候选关系后纠正了这一判断：真正的差异是 10 人中 9 人只有一个权威候选，1 人命中两个权威候选。这个复杂人员不允许直接套模板，而旧逻辑要求整批人员全部满足模板条件，因此整个 10 人批次退回完整分析，模型再次需要生成长 JSON。

最终修复不再采用“整批全部模板化或全部完整分析”的二选一方式：

1. 服务端先为所有可模板化人员计算 profile，并选择人数最多的 profile；选择结果不受人员顺序影响。
2. 主人群只调用一次 `derive-reconciliation-analysis-template`。
3. 多候选等复杂人员进入独立的 `reconcile-entity-batch` 兜底调用。
4. 兜底调用使用稳定派生的子 action ID，重试时能够恢复原调用。
5. 子 action 的 resource IDs、evidence manifest、输入证据引用和结果校验白名单都只包含复杂人员，不能读取或引用模板人群的证据。
6. 模板结果和复杂人员结果通过服务端合并，然后一次性完成批次落库。

独立代码审查曾发现两个重要问题并在合并前修正：模板组不能由第一个人员决定，必须选择最大人群；兜底调用的证据范围不能继续沿用原始整批清单。

## 重试与恢复后的执行路径

```text
读取冻结批次证据
  -> 计算人员模板资格与 profile
  -> 选择人数最多的模板组
      -> 已有模板检查点：直接复用
      -> 没有检查点：模型生成一次通用模板并保存
  -> 复杂人员使用独立子 action 完整分析
      -> 失败：保留模板检查点和工具调用进度
      -> 重试：复用模板，从复杂人员最近检查点继续
  -> 服务端合并两部分结果
  -> 精确覆盖批次工作项后落库
```

## 运维注意事项

- 合并代码后必须重启 API 和 Agent Worker，正在运行的旧进程不会自动加载 Python 代码修改。
- 已进入 `blocked_model_error` 且界面只允许终止的旧任务不能直接转换成新执行路径；应保留其审计事实，终止后创建新任务验证修复。
- 不应通过删除任务、清空失败记录或释放学校锁来绕过安全暂停。
- 如果再次出现无效 JSON，应优先查看安全元数据中的 HTTP 状态类别、传输尝试次数、失败 Skill、批次人数和请求 ID，再判断是上游响应格式、输出截断还是业务分组问题。
