API 接入对 Agent Graph 的影响

结论：增加“连接配置域”和一个 API 快照动作；不要为钉钉、企微各复制一条 Graph。

当前 agent-sync-graph-v2

来源类型被压成 CSV / Database

对话确认→ 学校锁→ materialize_sources
远程 CSV：下载、校验、冻结
Database：直接进入检查
API：Schema 有 kind，但运行时没有真实分支
inspect_sources→ normalize→ 对账/审批/执行

问题不是后半段 Graph 不够，而是 API 没有可重放的来源快照，也没有租户级连接生命周期。

推荐 agent-sync-graph-v3

连接配置与同步执行分离

① 连接配置域（Graph 外）

聊天识别“钉钉”→ Provider Catalog→ 安全凭据卡→ 确定性连接测试→ Connection Instance

不获取学校锁，不把 AppSecret 交给 LLM，不占用一次同步运行。

② 同步执行域（Graph 内）

任务确认→ 学校锁→ materialize_sources→ inspect→ normalize→ 原有治理链路
remote_csv → materialize_remote_authority
api → capture_api_authority_snapshot（新增 action）
database/local_csv → source_already_stable

钉钉和企微只在 Adapter 内不同；Graph 只认识 connector kind、能力和快照证据。

③ 统一数据合同

供应商原始记录→ 不可变 SourceSnapshot→ OrganizationRecord

部门要求 ID/名称/父级；老师要求 UserID/姓名/部门关系。手机号和邮箱允许缺失，避免真实 API 因隐私权限被误判为异常。

节点与 Skill 的判断

增加 action
在现有 materialize_sources 下增加 API 快照动作。
不增加厂商节点
不要创建 dingtalk_node、wecom_node，也不要把 OAuth 做成 Agent 节点。
升级现有 Skill
对话、来源检查、规范化版本升级；OAuth、分页、重试全部留在确定性 Adapter。

三种架构选择

点击一个方案；我推荐 B。

A

每个厂商一套 Graph

钉钉、企微分别增加认证、拉取、规范化节点。直观，但节点与测试会随厂商成倍增长。

B

通用 Graph + 专用 Adapter（推荐）

Graph 只增加通用 API 快照动作；厂商差异封装在 Adapter，后半段治理链路完全复用。

C

Graph 不变，检查时直接请求 API

改动最少，但分页期间数据会变化，难以审计、重放和幂等，不适合当前持久化 Graph。
