魔方 Agent01 · 问题定义
WHY GOVERNANCE

为什么需要数据治理？

同步只能搬运结果；治理要解释差异从哪里来、哪些字段可信，以及下一步能否安全处理。
01 · 系统独立维护

每个系统都在维护自己的“事实”

魔方、第三方平台和教务系统按各自业务新增、修改教师、学生、部门与班级，更新节奏和字段口径并不一致。同一条记录可能在一个系统里已经更新，在另一个系统里仍然缺失；单纯同步只能搬运某个来源的结果，无法判断谁是依据、为什么出现偏差，也无法留下后续治理需要的证据。

多源接入独立维护事实不一致
02 · 字段不同步

同一个人，字段也可能对不上

编号、电话令牌、邮箱、姓名、类别和班级可能缺失、改名、格式不同或发生漂移；姓名相同不代表身份相同，编号不同也不一定代表是两个人。治理需要先做字段规范化和身份候选召回，再用可引用的快照与证据区分缺失、冗余、冲突和普通字段差异，最后才能决定是自动处理还是交给人工确认。

字段差异身份候选证据核对
同步 = 接入层→治理 = 证据 + 分析 + 决策 + 执行验证 + 报告/回滚

魔方 Agent02 · 设计取舍
DESIGN CHOICE

为什么Agent-Graph更适合我们的治理任务？

我们的任务同时包含语义判断、人工审批和高风险写入，需要“AI 有弹性、流程有边界”。
Workflow

流程稳定，但语义弹性不足

步骤和分支预先写死，确定性强；遇到名称变体、缺失字段和多候选身份时，需要不断增加特判规则。扩展性差，不适合多数据源的数据治理系统。

难处理复杂歧义
普通 Agent

理解灵活，但边界不清晰

一个 Agent 同时掌握上下文、工具和多个阶段，容易产生幻觉、越过流程；失败后也难判断哪一步已经可信完成。面对大量数据时，还容易发生上下文溢出。

难恢复 · 难审计
Agent-Graph

让 AI 判断，让后端控流程

采用类似于 LangGraph 的架构，把长流程拆成可恢复的状态边界。对于多数据源、需要语义判断、人工审批的数据治理任务，既保留 Agent 的灵活性，又让 Graph 固定状态和可达路径；Agent 只在节点内处理语义，审批、权限、写入都由后端掌控。

最适合本项目
我们接受的成本增加 Schema、状态、租约、锁和版本管理。
换来的收益保留 LLM 处理歧义，同时让证据、权限、写入和恢复可控。

魔方 Agent03 · 三阶段安全检查
THREE GATES · DATA → AI → EXECUTION

三道安全门：分别守住接入、分析和执行

它们不是三个模型，而是数据治理链路中的三个后端检查点：数据接入要可信，AI 分析要有依据，治理执行要满足当前条件。
01 · 数据接入门

确认“输入数据可信”

对应来源接入与规范化：检查快照是否冻结、字段是否符合合同、每条输入是否被准确覆盖。
if snapshot.immutable
  and schema == "six_fields"
  and covered == batch_size:
    continue
else:
    route("abnormal_input_report")
02 · AI 分析门

确认“分析结论有依据”

对应身份索引与 LLM 分析：检查身份候选、服务端分类和 finding 证据；多候选冲突必须转人工。
if len(candidates) > 1:
    route("human_gate")
elif finding.evidence_refs:
    compile_solution()
else:
    block("missing_evidence")
03 · 治理执行门

确认“现在可以写入”

对应 mutation 计划与后端写入：检查锁、目标版本、审批哈希和幂等键，写入后还必须回读验证。
if lock.valid and plan.hash == approval.hash:
    result = execute_idempotent()
    verify(result.after)
else:
    block("stale_or_unapproved")
三道门的分工：数据接入门防止脏数据进入，AI 分析门防止无依据结论进入计划，治理执行门防止过期、未审批或重复操作写入目标。模型只能提交结构化结果，是否继续由后端决定。

魔方 Agent03 · 方案演进
THREE IMMUTABLE WORKFLOW VERSIONS

三代框架如何演进：legacy-v1 → new-agent-v1 → agent-graph-v1

Git 记录中的三个 top-level workflow_version 不是同一套代码的改名，而是三次架构边界的变化；旧任务保留原版本，新任务按版本路由。
第一代 · legacy-v1

legacy-v1

ReconciliationWorkflowService：固定阶段串联
snapshotsmatchingdifferencesanalysis
  • 按 snapshots → matching → differences → analysis 固定推进
  • 匹配、差异检测和分析分别由后端服务完成
  • 依赖旧实体模型、匹配质量门和历史任务路径
遇到的问题：前置匹配、向量/重匹配和质量门可能把任务挡在 AI 分析之前；旧实体模型与多源字段差异耦合较深，难支撑对话式任务、批量 Agent 和细粒度恢复。
第二代 · new-agent-v1

new-agent-v1

固定线性 Agent：阶段 Handler + 独立 Worker
phase handlerrun / locklease / retry
  • 改成接入、身份、分析、审批、执行、报告的 Agent 阶段
  • 引入持久化 run、event、checkpoint、lease 和 Skill/MCP 权限
  • 固定 Worker 只领取 new-agent-v1，历史版本不被覆盖
遇到的问题：阶段推进仍由固定 Handler 控制，Skill 还没有真正成为可调度的 sub-agent；大批次输出无效、模型调用失败或工具调查中断时，细粒度工作难以重放和定位，促成了 Graph 改造。
第三代 · agent-graph-v1

agent-graph-v1

服务端状态图 + Supervisor + 版本化 Skill/Sub-agent
allowed_actionsevidence manifestcheckpoint
  • Graph 固定节点、边和 guard，Supervisor 只能选择服务端候选动作
  • Sub-agent 只看当前证据清单，通过阶段工具提交结构化结果
  • 后端掌握锁、审批、幂等写入、回读验证、报告和回滚
仍遇到的问题：真实模型会返回无效 JSON，大批次会拖垮整批，工具失败可能丢失进度，失败报告还可能覆盖原始根因；后续用批次上限、模板复用、复杂项隔离、工具 checkpoint/安全重放和结构化错误逐项收窄故障范围。
版本边界：三种 workflow_version 独立保留；新任务按版本路由到对应 Worker，旧任务不原地改写。Git 记录证明，升级不是换模型，而是把固定流程逐步拆成可持久化、可审计、可恢复的边界。

PERSONAL TAKEAWAY

这个项目让我更清楚：AI 不只是模型，而是一套系统

真正的学习不只是完成一个功能，而是学会如何把不确定性放进边界、证据和反馈里。
01

先找到事实的主人

面对多源数据，先分清来源、口径和证据，AI 的判断才有落点。

02

把复杂问题拆成边界

Graph、Skill 和 checkpoint 让我学会把长链路拆成可以理解、可以恢复的阶段。

03

可靠性来自工程约束

权限、审批、幂等和验证不是额外负担，而是让模型能力真正可交付的条件。

04

从失败中学习架构

每一次 bug 都暴露一个边界缺口，也推动我把问题定位得更具体、把范围收得更小。

我最大的收获：做 AI 项目时，既要保持对新技术的好奇，也要用工程思维守住事实、权限和反馈，让系统值得被信任。
证据思维边界意识复盘习惯持续学习
